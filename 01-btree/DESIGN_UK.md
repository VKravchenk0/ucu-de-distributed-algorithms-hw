# Нотатка з проєктування

Охоплює, згідно з task.md R7.4: формат сторінок на диску, протокол
фіксації (commit) за схемою copy-on-write та схему звільнення простору.

## Формат сторінок на диску

Файл поділений на сторінки фіксованого розміру (`page_size`,
налаштовується при відкритті). Сторінка з id `0` завжди є
**сторінкою заголовка**; вона ж використовується як сентинел "null" в
інших місцях (наприклад, "ланцюжок вільного списку ще не створений"),
оскільки жодній реальній сторінці ніколи не присвоюється id `0`.

Кожен тип сторінки — заголовок, лист, внутрішня, вільного списку —
починається зі спільного 1-байтового тега типу за зміщенням 0, тож тип
будь-якої сторінки можна визначити лише за її першим байтом:
`0x2A` заголовок, `0x01` лист, `0x02` внутрішня, `0x03` вільний список.

### Сторінка заголовка (`src/page/header.rs`)

Оновлюється на місці при кожній фіксації (R2.3 — метадані не
використовують copy-on-write):

| зміщення | розмір | поле |
|---|---|---|
| 0 | 1Б | тег типу (`0x2A`) |
| 1 | 8Б | magic (`b"HWBTREE1"`) |
| 9 | 4Б | версія формату |
| 13 | 4Б | `page_size` |
| 17 | 8Б | `root_id` |
| 25 | 8Б | `next_page_id` (позначка high-water bump-алокатора) |
| 33 | 8Б | `free_list_head` (id першої сторінки в ланцюжку вільного списку на диску, `0` = немає) |
| 41 | 8Б | `free_count` (діагностика: загальна кількість записів у всьому ланцюжку) |

Файл, чия сторінка 0 не починається з тега+magic (новий або
нульового розміру файл), вважається **новим (fresh)**:
`Store::open_or_create` ініціалізує його порожнім листовим коренем на
сторінці 1 (R3.4). Файл із *дійсною* сторінкою заголовка, чий
`page_size` не збігається із запитаним викликачем, або чия версія
формату незрозуміла цій збірці, — окремий випадок: **помилка**
(`PageSizeMismatch` / `VersionMismatch`), а не новий бекенд, тож
повторне відкриття з неправильним розміром сторінки чи несумісним
старим файлом ніколи не може мовчки затерти реальні дані.

### Листова сторінка (`src/page/leaf.rs`)

Один лист B+-дерева на сторінку (R1.1: значення живуть лише в листках;
R3.1, R3.3):

```
| tag(1Б)=0x01 | page id(8Б) | key count(2Б) | entries... | unused |
```

Кожен запис — це `key_len(2Б) | key | val_len(2Б) | val`, один за
одним, без окремої таблиці зміщень/вказівників — цей формат на диску
навмисно плаский і послідовний, оскільки обмеження task.md прямо
вказують, що "slotted-page архітектура... не є обов'язковою".
Довільний доступ і бінарний пошук (R1.5) відновлюються натомість у
пам'яті: декодування сторінки будує невеликий кеш зміщень один раз
(один лінійний прохід по власних записах сторінки), і кожен подальший
виклик `get_key`/`get_val`/пошуку обслуговується з цього кешу — формат
*на диску* залишається простим, а *патерн доступу* залишається
O(1)/O(log n).

Id сторінки вбудований надлишково (він завжди відомий і з контексту
викликача) виключно як перевірка цілісності: декодування підтверджує,
що збережений id збігається з id, з якого сторінку було прочитано.

### Внутрішня сторінка (`src/page/internal.rs`)

```
| tag(1Б)=0x02 | page id(8Б) | key count N(2Б) | keys... | children... | unused |
```

Ключі: `key_len(2Б) | key`, повторюється N разів — лише розділювачі,
без значень, без вказівника на кожен ключ. Дочірні елементи:
`child page id(8Б)`, повторюється **N+1** разів, фіксованої ширини та
суцільно одразу після блоку ключів.

Це класичний макет B-дерева, який описує R1.1 з task.md ("внутрішні
вузли містять ключі-розділювачі та дочірні вказівники"): `child[0]`
покриває ключі `< key[0]`; `child[i]` (`0<i<N`) покриває
`[key[i-1], key[i])`; `child[N]` покриває `>= key[N-1]`. *N*
розділювальних ключів вузла розташовані *між* його *N+1* дочірніх
елементів, а не так, що кожен ключ пов'язаний 1:1 зі "своєю" дитиною.

### Сторінка вільного списку (`src/page/free_list.rs`)

```
| tag(1Б)=0x03 | page id(8Б) | next page id(8Б) | count(2Б) | free page ids... | unused |
```

`next page id == 0` позначає кінець ланцюжка. Записи мають фіксовану
ширину `u64` (кеш зміщень не потрібен). Дивіться "Збереження вільного
списку" нижче про те, як цей ланцюжок записується і відновлюється.

### Обмеження розміру запису

`check_limits`/`max_kv_size` (`src/page/mod.rs`) забезпечують R1.3
("кожна пара ключ/значення вміщується в одну сторінку"). Межа
випливає з внутрішньої сторінки: будь-який дійсний внутрішній вузол
повинен вміщувати одночасно 2 розділювальні ключі максимального
розміру плюс 3 дочірні елементи, щоб коли розбиття дочірнього вузла
змушує додати ще один ключ (3 ключі загалом), завжди гарантовано
існувала дійсна точка розбиття на 2 частини. Це *спрощення* порівняно
з попереднім проєктом, у якому кожен ключ був пов'язаний 1:1 зі
"своїм" дочірнім вказівником: у тій схемі зростання кореня могло
створити абсолютно новий корінь, що містить до 3 розділювачів,
скопійованих із 3-стороннього розбиття, яке після цього ніколи не
перевірялося повторно — це змушувало використовувати жорсткішу межу
`/3`. Завдяки справжньому просуванню медіанного ключа (median-key
promotion, див. нижче) переповнений вузол завжди дає рівно 2
результати плюс 1 просунутий ключ, ніколи 3, а щойно вирощений корінь
завжди мінімальний (1 ключ, 2 дочірні елементи) — тож межа послаблюється
з `(page_size - 46) / 3` до `(page_size - 39) / 2`. При `page_size=4096`
це `2028` байт корисного простору під ключ+значення замість `1350`.

## Протокол фіксації за схемою copy-on-write

`put` ніколи не змінює наявну сторінку (R2.1). Вставка ключа
рекурсивно спускається до цільового листа, а потім — на шляху назад
угору — або замінює один дочірній вказівник у копії батьківського
вузла (якщо рекурсивний результат вмістився в одну сторінку), або
вставляє нову пару `(розділювальний ключ, дочірній вказівник)` у
копію батьківського вузла, і якщо *це* спричиняє переповнення,
розбиває сам батьківський вузол через справжнє просування медіанного
ключа: ключ розбиття вилучається з обох половин і повертається для
вставки на рівень вище (розбиття листа натомість *копіює* свій перший
ключ угору, оскільки листи володіють своїми даними і не віддають
жодну їхню частину). Якщо розбивається сам корінь, дерево зростає на
один рівень під абсолютно новим, завжди мінімальним коренем (R1.6).
Стара версія кожної скопійованої/розбитої сторінки позначається як
*осиротіла*, але поки що не використовується повторно (див. звільнення
нижче).

`WriteTxn` (`src/storage/store.rs`) буферизує все це — записи сторінок
і звільнення — і робить це видимим лише при `commit(new_root)`:

1. Застосувати буферизовані записи сторінок до бекенду.
2. Додати осиротілі сторінки цієї транзакції до `pending_free`.
3. **Шлюз звільнення (reclamation gate)** (див. нижче): просунути
   `pending_free` у придатний для повторного використання вільний
   список лише якщо на цей момент немає активних читачів.
4. **Зберегти вільний список** у його ланцюжку на диску (див.
   "Збереження вільного списку" нижче).
5. Зберегти сторінку заголовка (id кореня, стан алокатора/вільного
   списку) — R2.3, оновлюється на місці.
6. `sync()` (довговічність), потім опублікувати новий корінь через
   **єдиний атомарний запис** в `AtomicU64` (R2.2). Це єдиний момент,
   коли нова версія дерева стає видимою для читачів.

Записувачі серіалізуються через єдиний `Mutex<WriterState>` (R5.3 —
модель з одним записувачем явно допустима). Читачі ніколи не
торкаються цього блокування: `ReadGuard` виконує лише
безблокувальне (wait-free) атомарне зчитування поточного кореня плюс
звичайні читання сторінок, тож записувач ніколи не може заблокувати
чи пошкодити читача, який виконується паралельно (R5.2). Оскільки
сторінки ніколи не змінюються на місці, читач, що захопив корінь `R`,
бачить повний, незмінений знімок усього, що досяжне з `R`, незалежно
від подальших дій записувача.

## Схема звільнення простору (R4)

Звільнені сторінки не використовуються повторно негайно — читач все
ще може обходити версію дерева, яка на них посилається. `Store`
відстежує глобальний лічильник читачів `AtomicUsize`, який
збільшується, коли `enter_read()` створює `ReadGuard`, і зменшується
(через `Drop`), коли той звільняється. Фіксація просуває
`pending_free` у придатний для розподілу вільний список лише якщо в
цей момент спостерігає лічильник читачів рівним точно нулю; інакше
сторінки просто накопичуються в `pending_free`, доки якась пізніша
фіксація не побачить лічильник рівним нулю. `alloc()` (R4.3) віддає
перевагу вилученню з вільного списку перед розширенням файлу.

**Чому це коректно, а не просто "зазвичай нормально":** сторінка `P`,
осиротіла при переході `V_i → V_{i+1}`, за побудовою недосяжна з
`V_{i+1}` і з будь-якого пізнішого кореня. Єдиний спосіб, яким будь-
який читач міг би коли-небудь звернутися до `P`, — це побачити
корінь `V_i` чи більш ранній і ще не завершити свій обхід. Шлюз
просуває `P` лише при фіксації, де лічильник читачів дорівнює нулю —
у цю мить, за визначенням, жоден читач не перебуває в процесі обходу,
тож кожен читач, який *міг би* побачити `V_i`, вже повністю завершив
роботу. Будь-який читач, що запускається після цього, читає лише
(монотонно зростаючий) поточний корінь, `V_{i+1}` чи пізніший — він
структурно не може дістатися до `P`. Перевірка ніколи не може
спрацювати зарано (звільнення, поки відповідний читач ще активний),
лише пізніше, ніж строго необхідно.

Це навмисно простіша з двох життєздатних схем — альтернатива це
відстеження епох за версіями (позначати кожного читача версією, з
якою він почав, позначати кожну звільнену партію версією, яка її
осиротила, звільняти партію, щойно найстаріший активний читач
просунувся повз неї), що звільняє простір раніше при стійкому
паралельному навантаженні на читання. Шлюз тиші (quiescence gate)
було обрано, тому що R5.3 прямо запрошує модель з одним записувачем,
а власні вимоги до тестів task.md (R7.3) перевіряють обмежене
зростання і паралельні читання як *окремі* тести, а не вимагають
одночасного виконання обох умов в одному комбінованому стрес-тесті —
тож єдина реальна вартість простішої схеми (звільнення може
затримуватися при безперервних паралельних читаннях без проміжку) не
є тим, що перевіряють обов'язкові тести, а "проста і коректна
реалізація є бажанішою" згідно з власними обмеженнями завдання.

### Збереження вільного списку

Вільний список (як придатний для повторного використання пул, так і
все, що ще очікує на шлюз тиші) зберігається у власному спеціальному
ланцюжку сторінок вільного списку при кожній фіксації, а не лише в
пам'яті. `WriterState` відстежує невеликий, постійний ланцюжок id
сторінок сховища для цього (`free_list_page_ids`), що виділяється
виключно через bump-алокатор — ніколи через вилучення з самого
`free_list`, що було б проблемою нерухомої точки (fixed-point):
вилучення змінює довжину списку, що змінює, скільки сторінок сховища
потрібно... Щойно сторінку сховища виділено таким чином, вона
використовується повторно (перезаписується на місці, як сторінка
заголовка — R2.3) назавжди, навіть якщо вільний список пізніше
зменшується: невелика, обмежена, постійна вартість заради схеми,
достатньо простої, щоб бути очевидно коректною.

Те, що записується при кожній фіксації, — це **об'єднання**
`free_list` і `pending_free`, а не лише просунутий `free_list` — це
безпечно, оскільки свіжий запуск процесу завжди починається з нулем
читачів (формулювання R4.2 "читач, який міг би це спостерігати" не
може пережити межу процесу), тож усе, що ще залишається в
`pending_free` на момент останнього завершення роботи, безумовно
безпечно звільнити тому, хто відкриє файл наступним. Сам
внутрішньопам'ятний шлюз тиші цим не зачіпається — він і надалі керує
тим, що придатне для використання як `free_list` *протягом життя
цього процесу* — розширюється лише те, що зберігається на диску, тож
процес, який завершується посеред партії, більше не втрачає ці
сторінки.

`Store::open_or_create` проходить ланцюжок від `header.free_list_head`
(слідуючи за `next page id` кожної сторінки, доки не `0`), щоб
відновити при повторному відкритті як внутрішньопам'ятний
`free_list`, так і набір придатних для повторного використання id
сторінок сховища.

## Бекенд mmap (`src/io/file_backend.rs`)

`std` не має вбудованої обгортки mmap, тож цей бекенд використовує
крейт [`memmap2`](https://docs.rs/memmap2) — обмеження task.md — це
"жодних зовнішніх бібліотек **B-дерева, сховища чи KV**", а
загальноцільова обгортка mmap, орієнтована на ОС, такою не є, тож
підключення цього крейта є прийнятним (на відміну від ручного
оголошення сирих прив'язок `extern "C"` `mmap`/`munmap`/`msync`
вручну, що лише відтворює те, що усталений крейт вже робить коректно
на різних платформах).

Конкретно, `MmapPageIo` використовує `memmap2::MmapRaw`:
`PageIo::read_page` / `write_page` / `sync` — усі приймають `&self`,
а не `&mut self` (один записувач, багато паралельних читачів, усі
через спільні посилання), тож зміни мають відбуватися через записи за
сирими вказівниками, а не через ексклюзивний `&mut [u8]`. `MmapRaw`
створений саме для цього — на відміну від `Mmap`/`MmapMut`, він надає
`as_ptr`/`as_mut_ptr` через `&self`, а не через `Deref`/`DerefMut`,
тож `read_at`/`write_at` копіюють байти туди й назад через сирий
вказівник, ніколи не матеріалізуючи `&[u8]`/`&mut [u8]` над пам'яттю,
яку ОС вважає зовнішньо спільною.

Щоб уникнути небезпеки повторного відображення під час паралельного
читання (читач тримає сирий вказівник у відображення, яке записувач
замінює через `munmap`+`mmap`), відображення резервує один великий,
фіксований діапазон віртуальних адрес одноразово при відкритті
(`DEFAULT_MAX_SIZE`, 1 ГіБ, через `MmapOptions::len`) і ніколи не
перевідображається протягом усього життя сховища. Зростання лише
розширює файл, що лежить в основі (`ftruncate`), у межах цієї
зарезервованої стелі — дешево на 64-бітному Linux, оскільки
невикористаний зарезервований віртуальний простір нічого не коштує
фізично, доки файл справді не розшириться в нього.
